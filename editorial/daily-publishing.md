# UK VISA FOLIO 毎日の記事制作マニュアル

## 選ぶ記事

日本語の既存下書きから1テーマだけ選ぶ。順番はファミリー（配偶者・婚約者・未婚パートナー）、技能労働者、ヘルスケア、学生。公開済み記事のタイトル、概要、見出しを読み、読者の疑問と答えが重なる記事は差し戻す。同じテーマの各言語版で扱う中心の疑問は揃える。

## 検索と執筆

- 対象地域の言語で、読者が使う検索語をウェブで調べる。最も自然で具体的な1語句をタイトルか見出しに使う。検索回数の根拠が得られない場合は数値や人気順位を書かない。
- 冒頭で疑問に答え、制度上求められることと、書類を整理する際の工夫を分けて説明する。専門用語は初出で説明し、自然な語順と読みやすい長さに整える。
- 英国ビザの条件、金額、期限、例外は現在のGOV.UKの一次情報で確かめ、該当する記述の近くにリンクを付ける。下書きはテーマの材料として使い、制度の根拠に使わない。本文のリンクは公式の一次資料に限る。
- 日本語は既存のタイトルラベルを維持する。日本語の断定や煽りを抑え、制度の記述は「GOV.UKでは〜を求めています」など出典の主体を明確にする。長いダッシュを使わない。1記事につき1種類のビザを扱い、個別の申請資格や結果を判断しない。
- 記事のテーマに合わせて、読者が抱えやすい書類整理の困りごとを一つ取り上げ、Stratovisaでどう整理できるかを具体的な作業で説明する。例として、原本と訳文をまとめる、チェックリストで準備状況を把握する、書類の形式とサイズを確認するなど。対応範囲を確認できない機能、申請内容の審査や申請結果を保証する表現は使わない。
- 紹介文とクーポンは、FAQがある場合はその直前に置く。クーポン案内を `[[STRATOVISA_OFFER]]` と `[[/STRATOVISA_OFFER]]` の行で囲み、35％オフの見出し、利用地域、コード、登録リンク、使い方の順に掲載する。日本語版には日本と英国のコードを別々に表示する。他言語版には対象地域で使えるコードを掲載する。割引はStratovisaのサービス料金に適用し、英国政府の申請料とIHSは対象外と明記する。
- 日本は `TABIDACHI`、英国は `ISSHONI`、インドは `SHUBHARAMBH`。韓国・台湾は専用コードの登録がないため、台帳で全地域対象とされている `SPECIALOFFER` を使う。専用リンクは確認済みのものだけを付ける。共通コードを案内する場合は、支払い前に手入力するよう説明する。

## 各言語の書類名

日本語は日本、英語は英国、韓国語は韓国、ヒンディー語はインド、繁体字中国語は台湾に居住する読者向けとする。言語から国籍を推定しない。居住地、国籍、書類の発行地が条件に関係する場合は区別する。

日本語版を土台に、対象地域の読者が実際に入手できる書類を使って説明する。発行機関の公式情報で現地の正式名称、発行元、何を証明するかを確かめ、英国側の提出条件や翻訳条件をGOV.UKで照合する。発行機関が書類を案内していても、それだけをUKVIでの受理の根拠にしない。対応する書類がなければ理由を明記し、英国の公式案内で確認できる書類だけを案内する。確認できない書類名や受理条件を推測しない。

## レビューと公開

自然な表現、出典、公開済み記事との重複、制作ルール、現地書類の5項目を言語ごとに確認する。現地書類は出典確認と合わせて判定する。確認結果を下書きの `qa_native`、`qa_citation`、`qa_similarity`、`qa_compliance` に記録し、すべて `PASS` の言語版を公開対象にする。あわせて `last_verified_at` に出典を確認した日を記録する。保留になった言語は指摘を記録し、修正後に再レビューする。合格済みの言語版は先に公開する。

### GitHub Actionsの運用

GitHub Actionsの標準ランナーで、確認済み下書きの選定・ビルド・公開を行う。文章の作成、翻訳、修正、レビューはこのワークフローの実行前に行う。APIキーは使用しない。「Daily article publication」の `preview` を有効にして手動実行すると、公開候補だけを確認できる。

定期実行は日本時間20時に、新規1テーマの公開を試みる。先行公開したテーマの追加言語版は15分ごとに確認し、レビューを通過済みなら追加公開する。確認済みの候補がない日は公開を見送る。配信時刻はGitHub Actionsの待ち時間とサイト側のデプロイで前後する。ビルドが失敗した場合はコミットしない。停止するには `FREE_ARTICLE_PUBLISH_ENABLED` を `false` にする。
